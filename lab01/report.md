## 1. Гүйцэтгэсэн ажил

Лабораторийн ажлын хүрээнд Raspberry Pi 3B болон Ubuntu WSL2 орчинд хоёр давхаргат IoT платформ байгуулж, ирмэг–үүлний MQTT холболт, үйлчилгээний нөөцийн хэрэглээ, мессеж дамжуулалтын саатал болон ачааллын үзүүлэлтүүдийг хэмжиж судлав.

### Алхам 0. Хэмжилтийн орчин бэлтгэх

Raspberry Pi болон Ubuntu WSL2 орчинд терминалуудыг тохируулж, SSH холболт, Docker Engine, сүлжээ болон системийн үндсэн үзүүлэлтүүдийг шалгав.

```bash
ssh -i "$env:USERPROFILE\.ssh\cnc302" -o IdentitiesOnly=yes cnc302@pi-team01.local
```

Raspberry Pi дээр:

```bash
vcgencmd get_throttled
vcgencmd measure_temp
docker --version
```

**Үр дүн:** Raspberry Pi болон Ubuntu орчинд холболт амжилттай тогтож, Docker үйлчилгээний ажиллагааг шалгав.

### Алхам 1. Raspberry Pi-ийн суурь хэмжилт

Raspberry Pi-ийн санах ой, CPU ачаалал, температур, хадгалалт болон throttling төлөвийг хэмжив.

```bash
cd ~/cnc302
OUTDIR=lab01/out bash tools/measure_stack.sh --role edge
```

**Үр дүн:** Нийт RAM 954 MiB, боломжтой RAM 583 MiB, температур 57.5°C, `get_throttled=0x0` байв.

### Алхам 2. Үүлний үйлчилгээний ажиллагааг хэмжих

Ubuntu орчинд EMQX, InfluxDB, Grafana болон Registry үйлчилгээнүүдийн эхлэх хугацаа, RAM болон CPU хэрэглээг тодорхойлов.

```bash
cd ~/cnc302
OUTDIR=lab01/out bash tools/measure_stack.sh --role cloud --startup
OUTDIR=lab01/out bash tools/measure_stack.sh --role cloud
```

**Үр дүн:** Дөрвөн үйлчилгээний нийт RAM хэрэглээ 385.01 MiB, бүрэн бэлэн болох хугацаа 13 секунд байв.

### Алхам 3. Ирмэг–үүлний MQTT гүүрийг тохируулах

Raspberry Pi дээр Mosquitto брокер болон ирмэгийн агентыг ажиллуулж, үүлний EMQX брокертой холбох тохиргоог хийв.

```bash
cd ~/cnc302/edge
make bridge
make up
make link
make agent
```

**Үр дүн:** Ирмэгийн үйлчилгээний нөөцийн хэмжилтээр Mosquitto 6.20 MiB, ирмэгийн агент 23.83 MiB, Docker демон 96.44 MiB RAM хэрэглэж байв.

### Алхам 4. MQTT мессеж дамжуулалтын саатлыг хэмжих

QoS 1 нөхцөлд 300 мессеж ашиглан loopback, LAN болон MQTT гүүрээр дамжуулах гурван замын саатлыг хэмжив.

```bash
cd ~/cnc302
PY=edge/.venv/bin/python

$PY tools/qos_latency.py --host localhost --port 1883 \
  --path loopback --qos 1 --count 300 --interval 0.05 \
  --csv lab01/out/04-latency-loopback.csv
```

**Үр дүн:** p99 саатал loopback-д 3.800 мс, LAN-д 84.422 мс, гүүрээр 26.277 мс байсан бөгөөд мессежийн алдагдал 0% байв.

### Алхам 5. Виртуал төхөөрөмжийн ачааллын туршилт

Ubuntu орчноос Raspberry Pi-ийн Mosquitto брокерт 0, 50, 100, 200 виртуал MQTT төхөөрөмжийн ачаалал үүсгэж, RAM, Swap, температур болон throttling үзүүлэлтүүдийг хэмжив.

Ubuntu-1 дээр:

```bash
~/mqtt-test-env/bin/python ~/mqtt_load.py --clients 100 --seconds 120
```

Raspberry Pi дээр:

```bash
cd ~/cnc302
edge/.venv/bin/python lab04/collect_metrics.py \
  --target edge --label load-100 \
  --seconds 180 --interval 5 --no-emqx
```

**Үр дүн:** 100 виртуал төхөөрөмж амжилттай холбогдож, 120 секундэд нийт 12,000 MQTT мессеж илгээв. Температурын хязгаарлалт бүртгэгдсэн тул төхөөрөмжийг дахин асааж, `get_throttled=0x0` нөхцөлд давтан хэмжилт эхлүүлэв.

### Алхам 6. Үүлний үйлчилгээнүүдийн RAM хэрэглээг харьцуулах

Үүлний үйлчилгээний нийт RAM хэрэглээг Raspberry Pi-ийн боломжтой санах ойтой харьцуулан тооцоолов.

```bash

  --format 'table {{.Name}}\t{{.MemUsage}}'
```

**Үр дүн:** Үүлний үйлчилгээний нийт RAM хэрэглээ 381.16 MiB байсан бөгөөд Raspberry Pi-ийн 583 MiB боломжтой санах ойтой харьцуулахад онолын хувьд 201.84 MiB нөөц үлдэхээр тооцоологдов.

### Алхам 7. Grafana хяналтын самбар

InfluxDB болон Grafana орчинд Raspberry Pi-ийн температур, боломжтой санах ой, MQTT гүүрийн төлөвийг хянах өгөгдлийн эх сурвалж болон дүрслэлийн тохиргоог хийв.


**Үр дүн:** `cnc302` өгөгдлийн сан болон Grafana хяналтын самбарын тохиргоог бэлтгэв.

Лабораторийн хэмжилтийн үр дүнг TXT болон CSV файлуудад хадгалж, Хүснэгт 1.1–1.6-д нэгтгэн, `lab01/report.md` тайланг боловсруулав.

## 4. Хяналтын асуултын хариулт

### 1. Гурван замын p99 саатал хэд дахин ялгаатай вэ? Гол шалтгаан юу вэ?

Loopback 3.800 мс, LAN 84.422 мс, гүүр 26.277 мс байв. Хамгийн их болон бага саатлын ялгаа **22.22 дахин** байна. Үүнд сүлжээний саатал, хэлбэлзэл нөлөөлсөн байх магадлалтай. Гол шалтгааныг нарийвчлан тогтооход нэмэлт хэмжилт шаардлагатай.

### 2. Хязгаарлагч нөөц RAM, CPU, сүлжээний аль нь байсан бэ?

100 төхөөрөмжийн үед MemAvailable дунджаар 561.58 MiB, Swap si/so 0/0 байсан тул RAM хязгаарлагч нөөц болоогүй. CPU болон сүлжээний үзүүлэлтүүдийг нэмэлтээр харьцуулж, үндсэн хязгаарлагчийг тогтоох шаардлагатай.

### 3. RAM-ийн дутагдал хэдэн MiB вэ? Pi 3B 2 GB RAM-тай бол платформ ажиллах уу?

Үйлчилгээнүүдийн нийт RAM хэрэглээ 381.16 MiB, боломжтой санах ой 583 MiB байна.

**381.16 − 583 = −201.84 MiB**

Иймээс RAM-ийн дутагдалгүй, онолын хувьд 201.84 MiB нөөцтэй. 2 GB RAM-тай бол санах ойн хувьд ажиллуулах боломжтой боловч CPU, диск болон сүлжээний нөөцийг мөн тооцох шаардлагатай.

### 4. cleanSession false-ийг true болговол юу өөрчлөгдөх вэ?

`false` үед брокер клиентийн session болон subscription мэдээллийг хадгална. Харин `true` үед өмнөх session устаж, шинэ session үүснэ. Өмнөх мессежийг хадгалах шаардлагагүй, түр хугацааны холболтод `true` тохиромжтой.

### 5. Өөр баг SITE=shutis ашиглавал юу болох вэ? Хэрхэн сэргийлэх вэ?

Ижил topic namespace ашигласнаар багуудын MQTT мессеж холилдох эрсдэлтэй. Үүнээс сэргийлэхийн тулд:

1. Баг бүрд ялгаатай topic namespace оноох.
2. Broker ACL ашиглан publish/subscribe эрхийг хязгаарлах.

### 6. get_throttled=0x50000 ямар утгатай вэ? Өмнөх хэмжилт хүчинтэй юу?

`0x50000` нь өмнө тэжээлийн хүчдэл буурч (`0x10000`), CPU-ийн хурд хязгаарлагдсан (`0x40000`) болохыг илэрхийлнэ. Одоогоор хязгаарлалт идэвхтэй биш.

Өмнөх хэмжилтэд эдгээр нөхцөл нөлөөлсөн байж болзошгүй. Лабораторийн шаардлагын дагуу тэжээл, хөргөлтийг шалгаж, `get_throttled=0x0` нөхцөлд хэмжилтийг давтан гүйцэтгэнэ.
